# [Deep Agents:LangChain的Agent Harness-13]从Deep Agents反向理解Agent Harness

Harness Enginering无疑是今年到目前为止AI Agent圈子最热的话题，网上充斥着大量关于Agent Harness的讨论和所谓的教程，你是否也被这些内容搞得云里雾里，不知道Agent Harness到底是什么，为什么要用Agent Harness。Deep Agents被视为LangChain平台针对Agent Harness的实现，通过前面12篇的内容，我们已经对Deep Agents有了比较深入的理解，现在我们利用Deep Agents提供的这些功能来反向理解Agent Harness，也许能帮助我们更好地理解Agent Harness的概念和意义。这篇文章的核心内容来源于[The Anatomy of an Agent Harness]https://www.langchain.com/blog/the-anatomy-of-an-agent-harness

## 1. Agent Harness是什么？

针对一个Agent，哪些部分属于Harness的范畴，Harness的边界在哪里？这个问题其实很好回到，Agent剥离LLM的部分都属Harness的范畴，换句话说：Agent = LLM + Harness。如果我们将Agent视为LLM的消费者（将LLM从Agent中剥离出来），那么可以认为整个Agent都是Harness，Harness Engineering就是Agent Enginering。

很多文章将Harness Engineering讲得很玄乎，还提出了所谓的层次划分。我觉得可以从这个角度来理解：我们希望的Agent是什么样子？LLM具有怎样的局限？Harness Engineering就是利用工程化的方式来弥补LLM的局限，构建出我们想要的Agent。对于Harness Engineering，它的起点是LLM目前具有的能力，终点就是我们对Agent的期望，它需要做的就是充分利用LLM的能力，同时提供必要的基础设施和工具，利用工程化的手段来弥补LLM的不足，构建出我们想要的Agent。

那么LLM能为Agent提供什么能力？它的不足之处由体现在何处呢？LLM本质上是一个具有**固化知识**和**推理能力**，并且**无记忆力**的语言模型，它能够理解和生成自然语言，具备一定的推理能力。虽然它拥有丰富的知识储备，但是知识体系在被训练的那一刻就已经被固化，从此以后不会由任何改变。LLM本质上是一个根据输入生成输出的函数,所有与它的交互都是**一锤子买卖**，它是无状态的，没有记忆力的，每次交互都是独立的。

还有一个重要的方面,LLM采用的Transformer架构本质上是一个深度度学习模型，也被称为深度神经网络。训练LLM的语料库具有广泛的来源，并通过预测下一个字符的方式来学习语言的规律和知识。就像一个人自降世那一刻，我们就把他关在一个小黑屋里，把存世的所有书籍都给它看，当他走出小黑屋的那一刻，他变拥有无比丰富的知识和强大的推理能力，但是他的世界观，道德准则和价值取向，我们不得而知，更不用说对一些规则的理解和遵守了。好在LLM只拥有一个聪明的大脑，就算它再邪恶，也不至于造成太大的伤害。但是一旦我们将LLM放在Agent中，相当于为它装备了强壮的四肢，那就不同了。

基于这些因素，在加上概率模型永远无法避免的**幻觉**，如果不加约束，Agent中的LLM就像一匹脱缰的千里马，Harness Engineering就为它系上缰绳，套上嚼子，装上马鞍，让它称为我们能够驾驭的坐骑，朝着我们期望的方向前进。所以Harness Engineering并不仅仅是锦上添花的东西，而是Agent能够正常运转的必要条件。Harness Engineering先保证LLM作对的事，然后在此基础上把事作对。

现在我们指导了LLM的能力和局限，对比一下我们对Agent的期望，我们就可以得出Harness需要做什么，并且怎么做了。

## 2. Harness 1： 基于文件系统持久化存储和上下文管理

**我们期望的Agent**

拥有持久存储，以便与真实数据交互，卸载与上下文不符的信息，并在会话之间持久保存工作。

**LLM的局限**

只能直接操作其上下文窗口内的知识，用户必须将内容直接复制/粘贴到模型中，这种用户体验非常笨拙，而且不适用于自动化的Agent。

**Harness解决方案**



**Deep Agents**

创建了基于Backend的后端，不仅包括一个抽象的文件系统，还提供了执行代码的Sandbox。在此基础上利用FileSystemMiddleware提供了一系列操作此文件系统的工具，包括：

- ls：列出目录；
- read_file：读取内容；
- write_file：写入文件；
- edit_file：精确编辑内容；
- glob：模式匹配查找；
- grep：文本搜索；
- execute：代码执行（仅限于可作为沙箱的后端存储）；



解答一个复杂的问题，或者规划一项复杂的任务，从来都不是一蹴而就的事情，而是一个不断迭代的过程。针对同一个问题采用不断迭代的方式进行求解的前提是上下文的保持，也就是要求Agent具有记忆力。所以我们希望一个具有良好记忆力的Agent，与LLM天生健忘的特性形成了鲜明的对比。两者之间的鸿沟就是Harness需要弥补的地方。对于这个问题，所有的Agent平台都提供相同的解法：为Agent绑定一个存储，基于对话（Conversation）存储上下文信息。

由于对话可能耗时很长，甚至中间件由于需要人工介入导致中断，在分布式环境下还可能会跨越不同的机器甚至网络，所以这个存储有时候还得是持久化的。高级的Agent还提供了**时间旅行**的功能，运行我们回到推理流程的某个时间点提供新的输入重新开始推理，相当于开启了一段**平行世界**。这进一步要求上下文的存储还不能只存储最新的状态，还得存储核心历史阶段的状态，LangChain基于Checkpoint的存储很好地解决了这个问题。存储整个的对话历史也是为了审计和调试的需要，毕竟LLM的推理过程是一个黑盒过程，我们只能通过输入和输出进行观察和分析，如果没有对话历史的存储，我们就无法知道Agent是如何得出某个结论的，也就无法知道它是哪里出了问题了。

这种基于会话的记忆属于短期记忆，Agent在每次对话中都可以访问之前的对话内容，从而保持上下文的连续性。但是这种记忆是有时效性的，一旦对话结束，之前的记忆就会丢失。有时我们还需要跨会话的长期记忆。Deep Agents利用FileSystenMiddleware构建了一个抽象的文件系统，并提供了一系列工具进行文件操作。

## 3. 解决LLM执行能力的问题

LLM自身虽然具有强大的推理能力，但它并不具备执行能力，也就是说它无法直接操作外部环境来完成任务。所以我们通过注册工具的方式来赋予LLM执行能力，并采用ReAct循环以迭代形式向前推进，形成了一个经典的循环：**Thought** → **Action** → **Observation** → ...

- Thought (思考)：模型分析当前现状，决定下一步该做什么，以及为什么要这么做;
- Action (行动)：模型从工具箱中选择一个工具（如：搜索、计算器、API调用）并执行;
- Observation (观察)：模型读取工具返回的结果（即外部世界的反馈）;
- Repeat (迭代)：模型根据新的观察结果，开始下一轮 Thought，直到找到最终答案;

但是，Agent只能执行其逻辑支持的工具。与其强迫用户为每个可能的操作构建工具，不如为代理提供一个像bash这样的通用工具，这样更合理的解决方案是避免这种情况。所以Harness需要为LLM提供bash工具来执行LLM生成的代码。`Bash + Code Execution`是让LLM拥有计算机并自主完成其余工作的重要一步。模型可以通过代码动态设计自己的工具，而不是局限于一组预先配置好的工具。

## 4. 为动态生成代码提供Sandbox和配套工具

既然Agent拥有了执行代码的能力，那么安全问题就不可避免了。LLM生成的代码可能会包含恶意代码，或者由于模型的幻觉而生成错误的代码，这些都可能对系统造成损害。因此，Harness需要提供一个安全的Sandbox环境来执行LLM生成的代码，以防止潜在的安全风险。

Deep Agents的Sandbox是其框架中核心的执行后端，专门为Agent提供一个安全、隔离且可配置的运行环境。不同于普通的本地工具，Sandbox是为了解决LLM生成代码的不可预测性而设计的生产级基础设施。在Deep Agents架构中，Sandbox不仅仅是一个Python解释器，而是一个完整的后端环境，提供了：

- 物理隔离：它在Agent与宿主系统之间建立边界，防止AI误删本地文件、窃取凭证或进行恶意网络操作;
- 权限赋予：与仅支持文件操作的其他后端（如Filesystem）不同，Sandbox后端会赋予Agent一个代码执行工具，允许其运行任意Shell命令;

Deep Agents的Sandbox具有如下的能力和特性：

- 代码执行与调试：Agent可以在沙箱内安装pip包、克隆GitHub仓库、运行测试脚本并查看输出结果，实现闭环开发；
- 持久化文件系统：提供类似于本地环境的文件管理能力，支持ls、read_file、write_file 等操作，Agent可以将沙箱作为其**工作台**；
- 状态可重现性：为每个任务提供干净、独立的环境，确保测试结果不会受到前一次运行的残留文件或环境变量影响；
- 支持并发与长时任务：支持同时启动多个沙箱运行不同任务，互不干扰，且可以离线运行耗时操作；

Deep Agents本身是一个高度集成的Agent Harness，它通过与第三方专业沙箱提供商集成来实现这些能力：

- E2B：基于MicroVM（Firecracker）技术，提供极高安全性且开源，适合代码解释器场景;
- Modal：基于gVisor隔离，擅长处理需要GPU或大规模批处理的高性能计算任务;
- Daytona：专注于开发环境的沙箱，支持Git原生操作，适合构建复杂的编码Agent;
- Runloop：专为AI训练和评估设计的动态沙箱环境。

除了为生成的代码提供作为安全执行环境的Sandbox之外，提供一些配套工具，比如预安装语言运行时和软件包、用于Git和测试的命令行界面、用于 Web 交互和验证的浏览器。这有助于创建从`代码编写`到`运行测试`,再到`查看日志`并`修复错误`的**代码自我验证循环**。

## 5. 具备自我学习和进化的能力

LLM自身就是一份被冻结和隔离的代码，永远不会发生改变，但是我们希望Agent能够不断地学习和适应用户的需求，提供更加个性化和智能化的服务。所以让Agent仅仅拥有基于对话的短期记忆还不够，因为这样的记忆仅仅是为了维护上下文的连续性。每个新的会话都从相同的状态开始，Agent无法从之前的经验中学到任何东西。此时需要一个跨对话的长期记忆系统，Agent记忆在**工作中**将值得学习的东西记录下来，并应用于后续的对话中，这样Agent就具备了自我学习和进化的能力。

Deep Agents在文件系统基础上构建了一个持久化的记忆系统`MemoryMiddleware`，它维护的内容总是会无选择地作为LLM的上下文。由于建立在文件系统上，所以LLM可以在任何时候利用操作文件系统的工具将直接认为有用的记下来。这种记忆系统不仅可以存储事实性的知识，还可以记录经验和学习过程，从而使得Agent具备了学习和进化的能力。

LLM的冻结与隔离还体现在知识体系的固化，所以它永远无法获取实时的信息，业务部了解**私域**环境下的知识和规则，目前为止RAG是最常见的解决方案。对于实时公共信息的提供，提供web-search这样的工具是一个不错的选择。

## 6. 解决上下文腐化（Context Rot）的问题

我们掌握的信息越多，所作出的决策未必就越正确，LLM也是如此。随着推理的不断推进，LLM的上下文中会积累越来越多的信息，这些信息有些可能是正确的，有些可能是错误的，甚至有些可能是相互矛盾的。这就导致了上下文腐化（Context Rot）的问题，也就是随着时间的推移，LLM的上下文中包含的信息质量会逐渐下降，从而影响LLM的推理能力和决策质量。Harness的解决方案很明确：只提供LLM在某个推理阶段真正需要的信息，其他的都不要提供。对于LLM来说，**少即是多**，只提供必要的信息，才能让LLM更好地发挥其推理能力。考虑到上下文信息主要包括：

- 作为对话历史的消息列表；
- 可用的工具列表；
- 系统指令；

由此决定了对应的解决方案：

- 对话历史的压缩：比较典型的做法直接删除相对陈旧的消息，或者对其进行摘要，Deep Agents利用注册的_DeepAgentsSummarizationMiddleware中间件来实现对话历史的自动摘要;
- 对话历史结构的自动修复：作为核心的上下文信息，作为对话历史的消息列表的结构和内容同等重要，设置可用说结构更加重要，比如消息的错位可能会导致**因果倒置**的问题。但是推理过程中的异常可能会导致消息列表的结构被破坏，所以让Agent具备自动修复消息列表结构的能力也是很有必要的。Deep Agents为此设计了的PatchToolCallsMiddleware；
- 无用工具的卸载：只为当前的推理任务保留最相关的工具，其他的工具都卸载掉，避免LLM换上**选择困难综合征**；
- Skills：采用渐进式披露的方式只为LLM提供当前阶段真正需要的系统指令，我们也可用进一步根据Skill选择工具集。Deep Agents利用SkillsMiddleware引入了Agent Skills；
- Multi-Agent: 通过引入多个Agent来分担不同的任务，每个Agent只需要关注自己负责的任务，从而减少每个Agent的上下文信息量。以Sub-Agent模式为例，当我们以类似于工具调用的方式来调用Sub-Agent时，不论Sub-Agent内部经历多少论的迭代，当前Main-Agent的上下文窗口中只会保留Sub-Agent最终的输出结果，从而为上下文窗口腾出了更多的空间来保留其他重要的信息。Deep Agents不仅提供了SubAgentMiddleware来支持内敛模式的Sub-Agent，还提供了AsyncSubAgentMiddleware来支持异步模式的Sub-Agent；

## 7. 有效地完成长程推理

生产环境的Agent需要解决的问题或者规划的任务基本上都不可能一蹴而就，很多都需要采用**大事化小**的策略，将复杂的问题拆解为多个可管理的小任务，然后逐步解决。而且步骤之间还可能存在依赖关系，前一个步骤的输出可能是后一个步骤的输入，中间任何一个环节出了问题都可能导致整个推理过程的失败。为此Deep Agents提供了TodoListMiddleware中间件，它不仅利用提示词指导LLM将采用任务分解的策略来完成复杂的任务，还提供响应的工具来保存当前推理状态：整个任务被划分为多少个步骤，哪些步骤的规划已经完成、哪些正在进行中、哪些还没有开始，不至于让LLM在长程推理过程中迷失方向。

ReAct循环是Agent普遍采用的推进模式，但是由于LLM总是具有**过度自信**的毛病，所以它倾向于过早地得出结论，或者在没有充分信息的情况下就做出决策，并且还认为自己给出的答案完美无缺。为了保证推理的质量，ReAct循环得换成**Ralph循环**。Ralph循环取自经典动画《辛普森一家》里的角色Ralph Wiggum。Ralph 在剧中表现得天真、反应慢，甚至有些“笨拙”，但他极其执着且总是处于某种奇怪的自循环状态。我们借此自嘲并精准定义了这一模式：哪怕LLM初始尝试失败了（像Ralph一样“笨”），但只要让它像死循环一样不断重试，最终也能通过量变引起质变，完成高难度任务。Ralph循环是一种Harness模式，它通过钩子拦截模型的退出尝试，并在一个干净的上下文窗口中重新注入原始提示，强制代理继续执行以完成目标。
