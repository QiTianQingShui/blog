# [FastMCP设计、原理与应用-09]让工具以后台任务形式调度执行

FastMCP针对后台任务协议的实现主要依赖于`Docket`和`Worker`，前者作为任务调度器负责创建任务并将其置于队列中，后者作为工作节点从队列中提取任务予以执行。FastMCP会默认创建一个`Worker`，我们可以采用代码或者命令行的形式创建多一个`Worker`。在介绍`Docket`和`Worker`之前，我们先通过一个简单的实例演示一个后台任务是如何被`Docket`调度并最终在某个`Worker`中执行的。

## 1. 利用Docket和Worker完成任务的调度与执行

在如下的程序中，我们定义了一个`long_running_task`函数作为一个需要以后台任务形式调度执行的长耗时操作。它具有两个可用自动注入的参数，`progress`参数指定的`Progress`对象用于设定执行进度，而`execution`参数指定的`Execution`对象表示当前被调度执行的任务（确切地说是任务的快照）。我们假设整个处理流程划分为5步，并通过调用`Progress`对象的`set_total`方法进行了设置。在接下来的5次循环迭代中，我们先通过`Execution`的状态确定任务是否被取消，如果是则直接抛出`CancelledError`异常。由于`Execution`仅仅是任务的一个快照，所以我们得先调用其`sync`方法进行状态同步。每次迭代都会异步等待一秒，并调用`Progress`对象的`increment`方法更新进度。

```python
from docket import Docket, Worker, Execution
from docket.dependencies import Progress,CurrentExecution
from docket._execution_progress import StateEvent, ProgressEvent
from docket.execution import ExecutionState
from datetime import datetime
import asyncio
from typing import cast

async def long_running_task(
        progress: Progress = Progress(),
        execution: Execution = CurrentExecution()
        ) -> None:
    await progress.set_total(5)
    for _ in range(5):
        await execution.sync() 
        if execution.state == ExecutionState.CANCELLED:
            print(f"[{datetime.now()}]Task cancellation detected, exiting early.")
            raise asyncio.CancelledError("Task was cancelled")
        await progress.increment()
        await asyncio.sleep(1)
    print(f"[{datetime.now()}]Task has been successfully executed")

async def track_task(execution: Execution):
    async for data in execution.subscribe():
        if data["type"] == "state":
            state:StateEvent = cast(StateEvent, data)
            print(f"[{datetime.now()}]State: {state['state']}")           
        else:
            progress:ProgressEvent = cast(ProgressEvent, data)
            print(f"[{datetime.now()}]Progress: {progress['current']}/{progress['total']}")

async def main():
    async with Docket(url="memory://") as docket:
        execution = await docket.add(long_running_task)()  # type: ignore
        async with Worker(docket=docket) as worker:
            worker_task = asyncio.create_task(worker.run_forever())
            track_task_task = asyncio.create_task(track_task(execution))
            try:
                while True:
                    await asyncio.sleep(1)
            except KeyboardInterrupt:
                print("exiting...")
            finally:
                worker_task.cancel()
                track_task_task.cancel()

if __name__ == "__main__":
    asyncio.run(main())
```

异步函数`track_task`用于跟踪任务得状态。我们调用`Execution`对象的`subscribe`方法订阅状态和进度变化，并实施输出。在main函数中，我们创建了一个基于内存存储的`Docket`对象，并调用其`add`方法对`long_running_task`函数进行注册和调度。我们根据此`Docket`对象创建了一个`Worker`对象，并调用其`run_forever`方法将它启动并持续执行下去，最后异步执行`track_task`方法跟踪任务的状态。从如下的输出可以看出，创建的任务先被添加到队列中（此时状态为QUEUED），然后被Worker提取出来执行（此时状态转换成RUNNING），执行完成后转换变成COMPLETED。我们在`long_running_task`函数中更新的进度在这里被实施输出。

接下来我们演示如何取消正在执行的任务。我们对main函数稍加改动：在完成调度并得到表示任务的`Execution`之后，异步等待了3秒，并调用其`mark_as_cancelled`方法将其标记为取消状态。该方法针对状态的标记会写入存储，所以`long_running_task`函数中的`Execution`对象需要调用`sync`方法同步此状态。

## 2. Docket

通过上个实例演示，我们应该对`Docket`和`Worker`之间的工作分工和协作关系有了大致的了解，接下来我们来详细介绍这两个核心对象。下面给出了作为任务调度器的`Docket`的几个核心的字段。

```python
class Docket(DocketSnapshotMixin):
    tasks: dict[str, TaskFunction]
    _redis: RedisConnection
    _result_storage: ResultStorage | None
    _cancel_task_script: _cancel_task | None

TaskFunction = Callable[..., Awaitable[Any]]

class _cancel_task(Protocol):
    async def __call__(
        self, keys: list[str], args: list[str]
    ) -> str
```

通过`TaskFunction`对象表示的操作（本质上是通过`Callable[..., Awaitable[Any]]`表示的一个异步函数）被调度之前先得完成注册，原因很简单：`Docket`需要将操作转换成能够放进队列的任务，而它使用的队列是Redis Stream，所以进入队列的任务必需能够被序列化，很显然`TaskFunction`不具备这一特质。所以`TaskRunction`还得放在内存中，对应于Docket的`tasks`字段表示的字典（Key表示任务的名称），注册的目的就是将`TaskFunction`添加到这个字典中。而所谓的调度本质上就是提取任务的元数据（可序列化），并将它们推入Redis Stream中。

整个任务调度、状态跟踪和取消都是基于Redis进行的，`Docket`的`_redis`字段返回的正是Redis的连接。`_cancel_task_script`字段提供一个用来取消任务执行的可执行对象，本质上是一段操作Redis的LUA脚本。由于不确定客户端获取执行结果的方式和时机，`Docket`只能将执行结果缓存起来，存储的地方就是`_result_storage`字段表示的`ResultStorage`对象。`ResultStorage`采用的存储依然是Redis。

```python
class Docket(DocketSnapshotMixin):
    def __init__(
        self,
        name: str = "docket",
        url: str = "redis://localhost:6379/0",
        heartbeat_interval: timedelta = timedelta(seconds=2),
        missed_heartbeats: int = 5,
        execution_ttl: timedelta = timedelta(minutes=15),
        result_storage: AsyncKeyValue | None = None,
        enable_internal_instrumentation: bool = False,
    ) -> None
```

如上所示的是Docket的构造函数的定义，它具有如下的参数：

- name：`Docket`的名称；
- url：Redis连接字符串。如果指定为`memory://`，它会利用本地内存存储模拟一个Redis（支持Redis的基本操作）；
- heartbeat_interval：`Docket`需要确定当前有效的`Worker`，所以要求每个`Worker`以固定的频率向自己（其实是Redis）发送心跳以确认它还活着，默认没2秒发送一次；
- missed_heartbeats：根据`heartbeat_interval`设置的频率计算某个时间段内应该接收到心跳次数，如果未收到的心跳的次数达到此参数设置的阈值，对应的Worker被视为不再可用，默认值为5次；
- execution_ttl：任务执行的超时时限，默认为15分钟；
- result_storage：上面介绍的任务执行结果的存储；
- enable_internal_instrumentation：是否为内部操作开启基于Open Telemetry跟踪的开关，默认关闭；

我们通过调用`Docket`的`register`方法对指定的`TaskFunction`对象进行注册。如果注册名称没有指定，默认采用函数的名称。如果在某个Python模块（假设模块名称为tasks_module）中定义了一个类型为`TaskFunction`序列的全局变量`tasks`，那么我们可以调用`register_collection`方法，并将`collection_path`参数书设置为`tasks_module:tasks`实施批量注册。

```python
class Docket(DocketSnapshotMixin):
    def register(self, function: TaskFunction, names: list[str] | None = None) -> None:
    def register_collection(self, collection_path: str) -> None:
    @overload
    def add(
        self,
        function: Callable[P, Awaitable[R]],
        when: datetime | None = None,
        key: str | None = None,
    ) -> Callable[P, Awaitable[Execution]]

    @overload
    def add(
        self,
        function: str,
        when: datetime | None = None,
        key: str | None = None,
    ) -> Callable[..., Awaitable[Execution]]
    def add(
        self,
        function: Callable[P, Awaitable[R]] | str,
        when: datetime | None = None,
        key: str | None = None,
    ) -> Callable[..., Awaitable[Execution]]

    async def get_execution(self, key: str) -> Execution | None
```

 上面定义的这几个重载的`add`方法用于任务调度。如果指定的函数没有经过注册，`add`方法会帮我们完成注册工作。如果`functon`参数被指定为一个字符串，它会被视为已经注册过的任务名称。add方法的`when`参数用于指定任务开始执行的时间戳，我们可以利用它实现延迟执行。`add`方法会根据提供的函数和执行时间戳创建一个`Execution`对象，它代表一个可被调度、被跟踪甚至改变状态的任务。`add`方法会`Execution`实施调度，我们可以利用返回的`Callable[..., Awaitable[Execution]]`对象得到这个`Execution`对象。某个被调度任务关联的`Execution`对象也可以通过`get_execution`方法提取。

 `Docket`还定义了如下两个重载的`replace`方法，它是 “取消旧任务 + 创建新任务” 的原子组合。如果用同一个key多次调用`replace`方法，Redis中永远只会保留最后一次设置的参数和执行时间（when）。如果传入的是函数对象且未注册，此方法会自动完成注册工作，确保这个任务在当前进程的“已知任务表”中。此方法依然返回`Callable[..., Awaitable[Execution]]`对象，我们可以利用它得到被被调度的`Execution`对象。在Redis内部，这是一个Lua脚本操作，保证了“删除旧的”和“插入新的”是不可分割的。

 ```python
class Docket(DocketSnapshotMixin):
    @overload
    def replace(
        self,
        function: str,
        when: datetime,
        key: str,
    ) -> Callable[..., Awaitable[Execution]]
    def replace(
        self,
        function: Callable[P, Awaitable[R]] | str,
        when: datetime,
        key: str,
    ) -> Callable[..., Awaitable[Execution]]    
```

对于已经被调度的任务，我们可以调用如下的`cancel`方法取消调度。如果任务尚未被执行，只需要将它从队列中移除就可以了。如果任务已经被某个`Worker`提取出来，准备执行或者已经在执行过程中，`Worker`也会利用Redis的`pub/sub`接收到取消的通知，它会“尽力”取消执行任务。另一个`clear`方会将排队的所有任务提取出来实施调度，最后清除队列。

```python
class Docket(DocketSnapshotMixin):
    async def cancel(self, key: str) -> None
    async def clear(self) -> int
```

## 3. Execution

通过调用`Docket`的`add`或者`replace`方法被调度的任务被转换成`Execution`对象，这是一个非常重要的对象。`Execution`不仅提供了任务执行的元数据信息（目标函数、任务名称、参数和预设的执行时间等），我们还可以利用它跟踪任务执行的进度和状态。除此之外，它还提供了一系列的方法使我们可以对任务进行干预，比如将任务标记为完成、失败和取消，通过redis同步当前状态，声明执行的Worker，以及发布和订阅任务状态和进度改变的事件等。

```python
class Execution:
    @property
    def docket(self) -> "Docket"
    @property
    def function(self) -> TaskFunction
    @property
    def args(self) -> tuple[Any, ...]
    @property
    def kwargs(self) -> dict[str, Any]
    @property
    def key(self) -> str
    @property
    def function_name(self) -> str
    @property
    def redelivered(self) -> bool
    @property
    def generation(self) -> int
```

上面列出了`Execution`一些字段：

- docket：作为调度器的Docket对象；
- function：承载操作的目标函数；
- args/kwargs：指定目标函数提供的参数列表；
- key：任务的唯一标识；
- function_name：函数名；
- redelivered：是否因在某个Worker中执行失败而重写投递；
- generation：任务的“代龄”。针对同一个Key调用Docket的replace会使任务的代龄自增，Worker从队列中提取“签收（Claim）”任务以及针对长耗时任务的执行过程中，可以利用它确定任务是否已经因为被替代而变得无效。

`Execution`承载的信息可以利用如下这个`as_message`方法序列化成`Message`，这是一个可以直接存储Redis的二进制字典。类方法`from_message`则执行反向操作利用`Message`对象生成`Execution`，并附上不参与序列化的目标函数。

```python
class Execution:
     def as_message(self) -> Message
    @classmethod
    async def from_message(
        cls,
        docket: "Docket",
        message: Message,
        redelivered: bool = False,
        fallback_task: TaskFunction | None = None,
    ) -> Self
Message = dict[bytes, bytes]
```

我们可以利用如下的三个方法将任务标记成完成、失败和取消状态。`get_result`方法则以阻塞方式获取任务执行的结果。

```python
class Execution:
    async def mark_as_completed(self, result_key: str | None = None) -> None
    async def mark_as_failed(
        self, error: str | None = None, result_key: str | None = None
    ) -> None
    async def mark_as_cancelled(self) -> None
    async def get_result(
        self,
        *,
        timeout: timedelta | None = None,
        deadline: datetime | None = None,
    ) -> Any
```

`Execution`类型还定义了如下这些有用的方法：

```python
class Execution:
    def get_argument(self, parameter: str) -> Any
    async def schedule(
        self, replace: bool = False, reschedule_message: "RedisMessageID | None" = None
    ) -> None
    async def claim(self, worker: str) -> bool
    async def sync(self) -> None
    async def is_superseded(self) -> bool
    async def subscribe(self) -> AsyncGenerator[StateEvent | ProgressEvent, None]
```
- get_argument：根据名称获取对应参数的值；
- schedule：调用任务。`Docket`的`add`和`update`方法均使用此方法来完成任务调度；
- claim：以原子操作的形式声明操作被指定的`Worker`“签收”，以阻止在其他Worker中被重复执行；
- sync：读取Redis同步任务最新状态；
- is_superseded：利用`generation`确定任务是否已经被替代；
- subscribe：利用Redis的`pub/sub`定于任务状态和进度改变的事件；

## 4. Worker

后台任务的调用本质上就是通过`Docket`将任务相关信息写入队列（Redis流）的过程，但是任务的执行最终由`Worker`来完成。我们来看看当我们构造一个`Worker`对象时，可以指定哪些用于控制器任务执行行为得配置项。

```python
class Worker:
    docket: Docket
    name: str
    concurrency: int
    redelivery_timeout: timedelta
    reconnection_delay: timedelta
    minimum_check_interval: timedelta
    scheduling_resolution: timedelta
    schedule_automatic_tasks: bool
    enable_internal_instrumentation: bool
    fallback_task: TaskFunction

    def __init__(
        self,
        docket: Docket,
        name: str | None = None,
        concurrency: int = 10,
        redelivery_timeout: timedelta = timedelta(minutes=5),
        reconnection_delay: timedelta = timedelta(seconds=5),
        minimum_check_interval: timedelta = timedelta(milliseconds=250),
        scheduling_resolution: timedelta = timedelta(milliseconds=250),
        schedule_automatic_tasks: bool = True,
        enable_internal_instrumentation: bool = False,
        fallback_task: TaskFunction | None = None,
    ) -> None:
        self.docket = docket
        self.name = name or f"{socket.gethostname()}#{os.getpid()}"
        self.concurrency = concurrency
        self.redelivery_timeout = redelivery_timeout
        self.reconnection_delay = reconnection_delay
        self.minimum_check_interval = minimum_check_interval
        self.scheduling_resolution = scheduling_resolution
        self.schedule_automatic_tasks = schedule_automatic_tasks
        self.enable_internal_instrumentation = enable_internal_instrumentation
        self.fallback_task = fallback_task or default_fallback_task
```

`Worker`类型的字段和构造函数的参数几乎时一一对应的，我们逐个说明每个字段的作用：

- docket：作为调度器的`Dcoker`对象；
- name：作为一标识`Worker`的名称；
- concurrency：控制该`Worker`同时能运行多少个协程任务，默认值为10；
- redelivery_timeout：重新交付超时（默认5分钟）。如果`Worker`领了任务但突然断电“失联”了，过了这个时间，后端`Dcoker`会认为该`Worker`已死，并将任务重新分配给别人;
- reconnection_delay：重连延迟。当底层数据库或消息中间件连接断开时，`Worker`等待多久尝试重新连接；
- minimum_check_interval：最小检查间隔。当队列为空时，`Worker`每次确定有没有新任务的时间频率。防止空跑时过度消耗CPU/网络;
- scheduling_resolution: 调度精度。针对“定时任务”（比如 10:00:00准时运行），Worker扫描时间轮的精度；
- schedule_automatic_tasks: 是否处理自动/定时任务。如果设为 False，该Worker只运行手动推送的任务，忽略cron类型的计划任务；
- enable_internal_instrumentation：内部监控插桩。开启后会收集性能指标（如任务耗时、成功率），通常用于对接Prometheus或日志系统；
- fallback_task: 兜底/后备任务。如果 Worker收到一个它“不认识”的任务类型（比如代码版本不匹配），它会转而运行这个默认函数，而不是直接崩溃或报错；

Worker具有不同的运行方式，分别对应如下这几个方法：

```python
class Worker:
    async def run_until_finished(self) -> None
    async def run_forever(self) -> None
    async def run_at_most(self, iterations_by_key: Mapping[str, int]) -> None
```
- run_until_finished(清空模式)：这是一种“干完就下班”的模式。Worker会不停地领任务，直到发现队列里目前已经没有待处理的任务了，它就会自动结束运行并退出。这种默认适用批处理任务，比如一次性扔进去1000个图片压缩任务，想等它们全跑完就关闭服务器。如果`Worker`正在跑的时候又有新任务进来，它会继续跑，直到真的“空了”为止。
- run_forever（长驻模式）：启动`Worker`并让它一致执行，这是最常用的生产模式。Worker启动后会永远守在任务队列旁。有任务就领，没任务就按`minimum_check_interval`设定的频率“抬头”看一眼。适用生产环境的任务处理节点。它不会主动退出，除非进程被杀死或收到关闭信号；
- run_at_most（限量/测试模式）：这是一个非常精细的控制模式。可以指定某些特定任务最多只能跑几次，例如：`await worker.run_at_most({"send_email": 5})`。这意味着当这个Worker累计执行了5次send_email任务后，它就会停止工作（即使队列里还有）。这种模式可以防止死循环，如果你写了一个“自我触发”的任务（任务跑完又把自己塞回队列），这个方法能防止它无限跑下去。它适合冒烟测试，只想验证前几次执行是否正常，不想跑完全部大数据量；

对于FastMCP，如果在具有后台任务调度需求的情况下（比如注册的工具、资源和提示词的后台任务模式被标记为`Optional`或者`Required`）,它会调用如下这个类方法`run`创建并启动一个单一的`Worker`。我们可以采用编程或者命令行的形式启动多个`Worker`，前提是我们采用真正的Redis作为存储。
