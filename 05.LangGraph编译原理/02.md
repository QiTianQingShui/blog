
# [LangGraph编译原理-02]面向通道的Agent状态

LangGraph编程基本围绕`StateGraph`进行，所以我们有必要对这个类型具有一个深刻的认识。这是一个泛型类型，四个泛型参数`StateT`、`ContextT`、`InputT`和`OutputT`分别表示状态、静态上下文、输入和输出类型，而且它们的类型都是一个`StateLike`类型。`StateLike`是四个类型的联合，其中前三个针对**类TypedDict和Dataclass的协议**。针对`StateLike`的定义，我们一般会使用`TypedDict`、`DataClass`和Pydantic模型。

```python
class StateGraph(Generic[StateT, ContextT, InputT, OutputT])

StateT = TypeVar("StateT", bound=StateLike)
StateLike: TypeAlias = TypedDictLikeV1 | TypedDictLikeV2 | DataclassLike | BaseModel
ContextT = TypeVar("ContextT", bound=StateLike | None, default=None)
InputT = TypeVar("InputT", bound=StateLike, default=StateT)
OutputT = TypeVar("OutputT", bound=StateLike, default=StateT)

class TypedDictLikeV1(Protocol):
    __required_keys__: ClassVar[frozenset[str]]
    __optional_keys__: ClassVar[frozenset[str]]
class TypedDictLikeV2(Protocol):
    __required_keys__: frozenset[str]
    __optional_keys__: frozenset[str]
class DataclassLike(Protocol):
    __dataclass_fields__: ClassVar[dict[str, Field[Any]]]
```

## 1. 节点、边、通道、ManagedValue和Schema

`StateGraph`使用`StateLike`类型的主要目的是利用它们对Schema的描述能力，所以对应的字段分别命名为`state_schema`、`context_schema`、`input_schema`和`output_schema`。创建`StateGraph`对象时`state_schema`类型是必需要指定的。如果作为输入输出Schema类型的`input_schema`和`output_schema`没有显式指定，它们默认与`state_schema`相同。

```python
class StateGraph(Generic[StateT, ContextT, InputT, OutputT]):    
    edges: set[tuple[str, str]]
    nodes: dict[str, StateNodeSpec[Any, ContextT]]
    branches: defaultdict[str, dict[str, BranchSpec]]
    channels: dict[str, BaseChannel]
    managed: dict[str, ManagedValueSpec]
    schemas: dict[type[Any], dict[str, BaseChannel | ManagedValueSpec]]
    waiting_edges: set[tuple[tuple[str, ...], str]]

    compiled: bool
    state_schema: type[StateT]
    context_schema: type[ContextT] | None
    input_schema: type[InputT]
    output_schema: type[OutputT]

    def __init__(
        self,
        state_schema: type[StateT],
        context_schema: type[ContextT] | None = None,
        *,
        input_schema: type[InputT] | None = None,
        output_schema: type[OutputT] | None = None,
        **kwargs: Unpack[DeprecatedKwargs],
    ) -> None:
        ...
        self.nodes = {}
        self.edges = set()
        self.branches = defaultdict(dict)
        self.schemas = {}
        self.channels = {}
        self.managed = {}
        self.compiled = False
        self.waiting_edges = set()

        self.state_schema = state_schema
        self.input_schema = cast(type[InputT], input_schema or state_schema)
        self.output_schema = cast(type[OutputT], output_schema or state_schema)
        self.context_schema = context_schema

        self._add_schema(self.state_schema)
        self._add_schema(self.input_schema, allow_managed=False)
        self._add_schema(self.output_schema, allow_managed=False)
```

`state_schema`、`input_schema`和`output_schema`这三个Schema类型针对数据成员的描述最终会转换成Pregel的**通道**或者`ManagedValue`，针对通道或者`ManagedValue`的创建实现在私有方法`_add_schema`方法中，该方法会将它们添加到`schemas`字段对应的两层字典中，第一层和第二层字典的Key分别为Schema类型和通道或者`ManagedValue`的名称。所有的通道和`ManagedValue`还会统一存储在`channels`和`managed`字段返回的字典中。

图由节点和边构建而成，添加的节点和确定的边被保存在`nodes`和`edges`字段中，运行时动态决定的**条件边**则被作为分支存储在`branches`字段中。`waiting_edges`字典用于存储**多对一**的边，即某个后续节点依赖多个**前序节点**，需要等所有前序节点都完成执行后才能执行。系统会为状态类型的每个成员创建一个通道或者映射为指定的`ManageValue`类型。

## 2. 通道的类型如何决定？

我们可以通过标注`Annotated`方式来决定通道和`ManagedValue`类型,具体规则如下：

- 默认采用的通道类型为`LastValue`；
- 可以利用`Annotated`的第二个参数指定通道或者`ManagedValue`类型，比如`Annotated[int, EphemeralValue]`;
- 如果希望的类型为`BinaryOperatorAggregate`,只需要利用`Annotated`的第二个参数指定对应的`reducer`函数就可以了。

如下的程序演示了上述这个规则。我们为状态类型`State`定义了四个成员：`foo`字段没有任何标注；`bar`提供了针对`EphemeralValue`类型的标注；`baz`提供了针对`operator.add`这个`reducer`函数的标注；`qux`标注的`RemainingStepsManager`是一个用于计算当前剩余步数的`ManagedValue`类型。

```python
from typing import Annotated, TypedDict,Required, NotRequired
from langgraph.graph import StateGraph
from langgraph.channels import EphemeralValue
from langgraph.managed.is_last_step import RemainingStepsManager
import inspect
import operator

class State(TypedDict):
    foo: str
    bar: Required[Annotated[int, EphemeralValue]]
    baz: Annotated[list[str],operator.add]
    qux: NotRequired[Annotated[int, RemainingStepsManager]]

def test_node(state:State):
    return {k:v * 2 for (k,v) in state.items()} # type: ignore

agent = (StateGraph(State)
    .add_node(test_node)
    .add_edge("__start__", "test_node")
    .add_edge("test_node","__end__")
    .compile())

for (name, chan) in agent.channels.items():
    if inspect.isclass(chan):
        print(f"{name}: {chan.__name__}")
    else:
        print(f"{name}: {chan.__class__.__name__}")
```

我们创建了一个包含单节点（`test_node`）的`StateGraph`对象，在将其编译成`Pregel`对象后，我们将它的`channels`字典存储的通道和`ManagedValue`的类型输出来（`channels`字典存储的是通道实例和`ManagedValue`类型，因为我们总是使用`ManagedValue`的静态方法`get`读取对应的值）。从如下的输出结果可以看出，四个状态成员对应的通道和`ManagedValue`的类型是吻合的。

```
foo: LastValue
bar: EphemeralValue
baz: BinaryOperatorAggregate
qux: RemainingStepsManager
__start__: EphemeralValue
__pregel_tasks: Topic
branch:to:test_node: EphemeralValue
```

如果状态Schema类型没有`__annotations__`属性，比如基础的内置类型和容器类型，此时整个状态将视为一个整体，并为其创建一个名为`__root__`的单一通道，通道类型为`LastValue`。如下这个将字符串作为状态Schema类型的演示程序体现了这一点：

```python
from langgraph.graph import StateGraph
from langgraph.channels import LastValue

def test_node(state:list):
    return state * 2

agent = (StateGraph(list)# type: ignore 
    .add_node(test_node)# type: ignore 
    .add_edge("__start__", "test_node")
    .add_edge("test_node","__end__")
    .compile())
assert agent.invoke(input= ["foobar"]) == ["foobar", "foobar"]
assert isinstance(agent.channels["__root__"], LastValue)
```

## 3. 输入和输出通道如何决定？

如果没有显式指定输入和输出Schema类型，它们将于状态共享相同的Schema，而且状态成员对应的通道将默认作为输入和输出通道。由于`ManagedValue`是只读的，所以不能作为输入；而且它一般用于返回运行时的状态，所以也不作为输出。其实`__init__`方法针对Schema的构建已经体现了这一点：针对输入和输出Schema调用`_add_schema`方法时，将`allow_managed`参数设置为`False`。

```python
self._add_schema(self.state_schema)
self._add_schema(self.input_schema, allow_managed=False)
self._add_schema(self.output_schema, allow_managed=False)
```

但是对于由`StateGraph`编译生成的`Pregel`对象，会将输入通道统一设置为`__start__`，所以我们提供的**整个输入**将统一写入此通道。`__start__`通道将会触发执行同名的节点，后者会将输入拆解写入对应的通道，然后驱动执行**入口节点**。对于上面演示程序创建的agent，我们可以通过如下的断言来证明这一点。

```python
assert agent.input_channels == "__start__"
assert agent.output_channels == ["foo", "bar", "baz"]

input:State={
    "foo": "abc",
    "bar": 123,
    "baz": ["a", "b"]
}

result = agent.invoke(input)
print(result)
assert result == {
    "foo": "abcabc",
    "bar": 246,
    "baz": ["a", "b", "a", "b","a", "b"]
}
```

如果使用`crate_agent`函数创建Agent，可以进一步标注如下几个类型来显式控制某个状态成员的输入输出特性：`OmitFromInput`和`OmitFromOutput`分别表示将指定的状态成员从输入或者输出Schema中剔除，`PrivateStateAttr`则表示同时从输入和输出Schema中剔除，成为一个内部使用的**私有状态成员**。

```python
@dataclass
class OmitFromSchema:
    input: bool = True
    output: bool = True
OmitFromInput = OmitFromSchema(input=True, output=False)
OmitFromOutput = OmitFromSchema(input=False, output=True)
PrivateStateAttr = OmitFromSchema(input=True, output=True)
```

但是针对它们的标注对于直接利用`StateGraph`构建的Agent是无效的。如下的演示程序成分说明了这一点：

```python
from typing import Annotated
from langgraph.graph import StateGraph
from langchain.agents import create_agent,AgentState
from langchain_openai import ChatOpenAI
from langchain.agents.middleware.types import OmitFromOutput,OmitFromInput,PrivateStateAttr
from dotenv import load_dotenv

load_dotenv()

class State(AgentState):
    foo: str
    bar: Annotated[str, OmitFromOutput]
    baz: Annotated[str, OmitFromInput]
    qux: Annotated[str, PrivateStateAttr]

def test_node(state:State):
    return state

agent = (StateGraph(State)
    .add_node(test_node)
    .add_edge("__start__", "test_node")
    .add_edge("test_node","__end__")
    .compile())

assert agent.input_channels == "__start__"
assert agent.output_channels == ['messages', 'jump_to', 'structured_response', 'foo', 'bar', 'baz', 'qux']   

agent = create_agent(
    model=ChatOpenAI(model="gpt-5.2-chat"),
    state_schema=State)

assert agent.input_channels == "__start__"
assert agent.output_channels == ['messages', 'structured_response', 'foo', 'baz']
```
