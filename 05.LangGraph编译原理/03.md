# [LangGraph编译原理-03]深入系统地了解一下状态图的“节点”

`StateGraph`通过添加节点和边这两个核心操作来构建具有期望结构的图。节点在LangGraph中如何描述？为什么我们可以将节点定义成签名自由的函数？什么样的对象可以直接注入节点函数？节点函数返回字典和`Command`有什么不同？如何控制节点执行采用的重试策略和缓存策略？工具存在一个怎样的节点中？这些问题都可以在本篇文章中找到答案。

## 1. StateNodeSpec

添加的节点被转换成`StateNodeSpec`对象被添加到`nodes`字段中。`StateNodeSpec`类型定义如下：

```python
@dataclass(slots=True)
class StateNodeSpec(Generic[NodeInputT, ContextT]):
    runnable: StateNode[NodeInputT, ContextT]
    metadata: dict[str, Any] | None
    input_schema: type[NodeInputT]
    retry_policy: RetryPolicy | Sequence[RetryPolicy] | None
    cache_policy: CachePolicy | None
    ends: tuple[str, ...] | dict[str, str] | None = EMPTY_SEQ
    defer: bool = False
```

如下所示相关字段说明：

- **runnable**：以`StateNode`对象的形式承载节点的执行功能；
- **metadata**：附加在节点上的辅助信息，会自动附加到捕捉到的跟踪记录；
- **input_schema**: 输入Schema类型；
- **retry_policy**：失败重试策略；
- **cache_policy**：针对节点执行结果的缓存策略；
- **ends**：该节点执行完毕后指向的下游节点；
- **defer**：延迟执行标志。如果设为`True`，该节点在满足触发条件后不会立即占用主线程执行，而是被放入异步队列中等待，常用于处理长耗时任务或需要特定调度时机的任务。

## 2. StateNode

有过LangGraph编程经验的人都知道：我们总是以函数的方式来定义节点，基于函数的节点定义方式是由表示节点的`StateNode`类型定义决定的。`StateNode`是一个类型别名，是对多个具有不同元素组合的Node协议类型的联合。

```python
StateNode: TypeAlias = (
    _Node[NodeInputT]
    | _NodeWithConfig[NodeInputT]
    | _NodeWithWriter[NodeInputT]
    | _NodeWithStore[NodeInputT]
    | _NodeWithWriterStore[NodeInputT]
    | _NodeWithConfigWriter[NodeInputT]
    | _NodeWithConfigStore[NodeInputT]
    | _NodeWithConfigWriterStore[NodeInputT]
    | _NodeWithRuntime[NodeInputT, ContextT]
    | Runnable[NodeInputT, Any]
)
```

如下所示的是`_Node`协议类型的，输入类型被定义成泛型参数`NodeInputT_contra`，被绑定为`StateLike`类型。节点的执行体现在唯一的`__call__`方法上，意味着具有兼容签名的可执行对象都可以表示为节点，函数自然也可以。

```python
class _Node(Protocol[NodeInputT_contra]):
    def __call__(self, state: NodeInputT_contra) -> Any: ...
NodeInputT_contra = TypeVar("NodeInputT_contra", bound=StateLike, contravariant=True)
```

由于节点在执行是出入需要依赖输入参数外，还需要一些运行时相关的信息，比如表示当前配置的`RunnableConfig`、向输出流实时写入数据的`StreamWriter`、表示长期存储的`BaseSotre`和表示当前运行时的`Runtime`。由于节点大部分以函数的形式定义，那么最方便的获得它们的方式肯定是**参数注入**。`StateNode`其他一系列联合成员类型旨在提供不同的`__call__`方法签名，以支持针对这些对象的不同组合。

```python
class _NodeWithConfig(Protocol[NodeInputT_contra]):
    def __call__(self, state: NodeInputT_contra, config: RunnableConfig) -> Any: ...
class _NodeWithWriter(Protocol[NodeInputT_contra]):
    def __call__(self, state: NodeInputT_contra, *, writer: StreamWriter) -> Any: ...
class _NodeWithStore(Protocol[NodeInputT_contra]):
    def __call__(self, state: NodeInputT_contra, *, store: BaseStore) -> Any: ...
class _NodeWithWriterStore(Protocol[NodeInputT_contra]):
    def __call__(self, state: NodeInputT_contra, *, writer: StreamWriter, store: BaseStore) -> Any: ...
class _NodeWithConfigWriter(Protocol[NodeInputT_contra]):
    def __call__(self, state: NodeInputT_contra, *, config: RunnableConfig, writer: StreamWriter) -> Any: ...
class _NodeWithConfigStore(Protocol[NodeInputT_contra]):
    def __call__(self, state: NodeInputT_contra, *, config: RunnableConfig, store: BaseStore) -> Any: ...
class _NodeWithRuntime(Protocol[NodeInputT_contra, ContextT]):
    def __call__(self, state: NodeInputT_contra, *, runtime: Runtime[ContextT]) -> Any: ...
class _NodeWithConfigWriterStore(Protocol[NodeInputT_contra]):
    def __call__(
        self,
        state: NodeInputT_contra,
        *,
        config: RunnableConfig,
        writer: StreamWriter,
        store: BaseStore,
    ) -> Any: ...
```

由于`Runnable[NodeInputT, Any]`也是Node众多联合成员的一份子，所以它也可以表示一个节点。不要忘了Agent本身是一个`Pregel`对象，也继承自`Runnable`类型。也就是说构建Agent的图是一个**可组合**的结构，Agent可以作为一个节点作为另一个Agent的一部分。当一个Agent不足以完成推理任务的情况下，我们很容易将多个Agent编排到同一图中，最终创建一个新的Agent。

再补充一点，目前我们具有两种创建Agent的方式，一种是调用`create_agent`工厂函数，另一种则是采用LangGraph。这两种都很有用，并不是后者用于替代前者。实际上`create_agent`也通过LangGraph实现的，它用于标准场景（如典型的ReAct循环）的Agent构建，为我们屏蔽了手动`add_node`和`add_edge`的繁琐过程。只有在这种标准Agent无法满足需求时，我们一般采用使用LangGraph针对复杂流程的编排能力。即使在使用LangGraph的时候，我们很多情况下也会使用`create_agent`创建的Agent作为它的一个节点。

## 3. 除了添加节点，add_node方法还可以做更多

`StateGraph`定义了如下五个重载的`add_node`方法向构建的图添加节点。除了作为节点的`StateNode[NodeInputT, ContextT]`对象外，我们还可以利用相关的参数指定延迟执行开关、元数据、失败重试和缓存策略、下游节点等。

```python
class StateGraph(Generic[StateT, ContextT, InputT, OutputT]):
    @overload
    def add_node(
        self,
        node: StateNode[NodeInputT, ContextT],
        *,
        defer: bool = False,
        metadata: dict[str, Any] | None = None,
        input_schema: None = None,
        retry_policy: RetryPolicy | Sequence[RetryPolicy] | None = None,
        cache_policy: CachePolicy | None = None,
        destinations: dict[str, str] | tuple[str, ...] | None = None,
        **kwargs: Unpack[DeprecatedKwargs],
    ) -> Self

    @overload
    def add_node(
        self,
        node: StateNode[NodeInputT, ContextT],
        *,
        defer: bool = False,
        metadata: dict[str, Any] | None = None,
        input_schema: type[NodeInputT],
        retry_policy: RetryPolicy | Sequence[RetryPolicy] | None = None,
        cache_policy: CachePolicy | None = None,
        destinations: dict[str, str] | tuple[str, ...] | None = None,
        **kwargs: Unpack[DeprecatedKwargs],
    ) -> Self

    @overload
    def add_node(
        self,
        node: str,
        action: StateNode[NodeInputT, ContextT],
        *,
        defer: bool = False,
        metadata: dict[str, Any] | None = None,
        input_schema: None = None,
        retry_policy: RetryPolicy | Sequence[RetryPolicy] | None = None,
        cache_policy: CachePolicy | None = None,
        destinations: dict[str, str] | tuple[str, ...] | None = None,
        **kwargs: Unpack[DeprecatedKwargs],
    ) -> Self:

    @overload
    def add_node(
        self,
        node: str | StateNode[NodeInputT, ContextT],
        action: StateNode[NodeInputT, ContextT] | None = None,
        *,
        defer: bool = False,
        metadata: dict[str, Any] | None = None,
        input_schema: type[NodeInputT],
        retry_policy: RetryPolicy | Sequence[RetryPolicy] | None = None,
        cache_policy: CachePolicy | None = None,
        destinations: dict[str, str] | tuple[str, ...] | None = None,
        **kwargs: Unpack[DeprecatedKwargs],
    ) -> Self:

    def add_node(
        self,
        node: str | StateNode[NodeInputT, ContextT],
        action: StateNode[NodeInputT, ContextT] | None = None,
        *,
        defer: bool = False,
        metadata: dict[str, Any] | None = None,
        input_schema: type[NodeInputT] | None = None,
        retry_policy: RetryPolicy | Sequence[RetryPolicy] | None = None,
        cache_policy: CachePolicy | None = None,
        destinations: dict[str, str] | tuple[str, ...] | None = None,
        **kwargs: Unpack[DeprecatedKwargs],
    ) -> Self:
```
 
`StateGraph`旨在利用重载的方式解决如下两个问题：

- 如果没有通过`input_schema`执行输入Schema，将直接使用表述状态的Schema类型；
- 如果没有指定节点名称，函数名将作为节点名。

## 4. 节点函数两种返回类型有何不同？

从`StateNode`众多联合成员类型的`__call__`方法的签名可以看出，LangGraph并未对添加的节点函数的返回类型做出严格的规定，它的返回值主要具有如下几种形式：

- 利用返回的字典（`dict`或者`TypedDict`）对状态进行增量更新。如果状态Schema类型为Pydantic模型，也可以直接返回状态对象；
- 利用返回的`Command`对象，在实现增量更新状态的同时，还可以实现针对新节点的跳转。

### 4.1 增量状态更新

在Agent整个处理流程中，节点函数主要通过**增量更新相应的状态成员**，**更新的状态成员最终写入对应通道**、**执行订阅变更通道节点**的方式向前推进，所以节点函数返回值的主要目的是描述它对通道的写入意图。如果仅仅是单纯地增量更新状态，我们只需要返回一个**字典**或者**Pydantic模型**。

```python
from typing import Annotated, Any 
from langgraph.graph import StateGraph
from pydantic import BaseModel, Field
import operator

class State(BaseModel):
    nodes: Annotated[list[str], operator.add, Field(default_factory=list)]
    remarks: str|None = None

def foo(state:State)->dict[str,Any]:
    return {"nodes": ["foo"]}

def bar(state:State)->State:
    return State(nodes =["bar"])

agent = (StateGraph(State)
    .add_node(foo)
    .add_node(bar)
    .set_entry_point("foo")
    .set_finish_point("bar")
    .add_edge("foo", "bar")).compile()

result = agent.invoke(input= State(nodes=["__start__"]))
assert result["nodes"] == ["__start__", "foo", "bar"]
```

在上面的演示程序中，我们以一个Pydantic模型的形式定义了作为状态Schema的类型`State`，列表类型的字段`nodes`用于记录流程执行的节点。先后执行的`foo`和`bar`节点分别返回一个字典和`State`对象将自己的名称添加到`nodes`列表中。

### 4.2 返回Command

`Command`是一个**全能控制器**。它的核心意义在于：将**状态更新**、**流程控制**和**人工交互**封装在一个对象中，允许节点动态地改写图的预设行为。

```python
@dataclass(**_DC_KWARGS)
class Command(Generic[N], ToolOutputMixin):
    graph: str | None = None
    update: Any | None = None
    resume: dict[str, Any] | Any | None = None
    goto: Send | Sequence[Send | N] | N = ()

    PARENT: ClassVar[Literal["__parent__"]] = "__parent__"

N = TypeVar("N", bound=Hashable)

class Send:
    node: str
    arg: Any
```

`Command`具有如下的字段成员：

- **graph**：指定指令的作用域。在子图中返回通过`Command(graph=Command.PARENT, goto="outside_node")`这种形式创建的`Command`对象，可以控制父图的跳转；
- **update**：用于增量更新状态成员；
- **resume**：专门用于人机交互（HITL）场景。在中断后的恢复调用时，我们利用它指定Resume Value；
- **goto**：利用指定的节点或者`Send`对象跳转到指定的节点。

在我的文章“[__pregel_tasks通道——成就“PUSH任务”的功臣](https://blog.csdn.net/JaydenAI/article/details/157836250)”中，我谈到驱动节点执行由两种方式，一种是基于通道订阅的**PULL模式**，另一种就是利用`Send`对象的**PUSH模型**。Pregel内部维护一个名为`__pregel_tasks`的`Topic`类型的通道（如果你足够仔细，会发现前面演示实例中输出的通道列表里有它），它存放的就是`Send`对象。在为下一个步生成执行任务时，作为执行引擎的Pregel会利用通道订阅确定执行的节点并生成对应的任务外，还会读取此通道提取`Send`对象来生成任务。

`Send`类型的定义很简单，只包含两个字典，分别是代表执行节点名称的`node`字段，以及代表输入参数的`arg`字段。当某个节点需要根据状态跳转到一个或者多个节点实现动态路由，可以针对目标节点的名称和所需参数创建对应的`Send`对象，并作为节点函数返回值。

在如下的演示程序中，我们将`State`类型的`nodes`定义成一个二元组的列表，我们通过此二元组表示执行的节点名称和输入参数。我们定义了`foo`、`bar`和`baz`三个节点，入口节点返回一个`Command`对象，处理利用设置其`update`字段更新`nodes`状态成员外，还创建了包含两个`Send`对象的列表作为它的`goto`字段，实现了指向节点`bar`和`baz`的跳转。

```python
from typing import Annotated ,Any
from langgraph.graph import StateGraph
from langgraph.types import Command, Send
from pydantic import BaseModel
import operator

class State(BaseModel):
    nodes: Annotated[list[tuple[str,Any]], operator.add] = [] 

def foo(state:State)->Command:
    return Command(
        update = {"nodes": [("foo","N/A")]},
        goto= [Send(node="bar", arg="foo->bar"), Send(node="baz", arg="foo->baz")],
    )

def bar(state:Any)->State:
    return State(nodes =[("bar", state)])

def baz(state:Any)->State:
    return State(nodes =[("baz", state)])

agent = (StateGraph(State)
    .add_node(foo) 
    .add_node(bar) # type: ignore
    .add_node(baz) # type: ignore
    .set_entry_point("foo")
    ).compile()

result = agent.invoke(input= State(nodes=[]))
assert set(result["nodes"]) == set([('foo', 'N/A'), ('bar', 'foo->bar'), ('baz', 'foo->baz')])
```

值得一提，如果某个节点同时设置了后续节点的边，即使该节点利用返回的`Command`实现了指向另一个节点的跳转，这条边指定的后续节点**依然会执行**,如下的演示程序证实了这一点。

```python
from typing import Annotated
from langgraph.graph import StateGraph
from langgraph.types import Command
from pydantic import BaseModel
import operator

class State(BaseModel):
    nodes: Annotated[list[str], operator.add] = []

def foo(state:State)->Command:
   return Command(
        update = {"nodes": ["foo"]},
        goto= "baz"
    )   

def bar(state:State)->State:
    return State(nodes =["bar"])

def baz(state:State)->State:
    return State(nodes =["baz"])

agent = (StateGraph(State)
    .add_node(foo) 
    .add_node(bar) 
    .add_node(baz) 
    .set_entry_point("foo")
    .set_finish_point("baz")
    .add_edge("foo", "bar")
    .add_edge("bar", "baz")
    ).compile()

result = agent.invoke(input= State(nodes=[]))
assert (result["nodes"] ==  ['foo', 'bar', 'baz', 'baz'] 
or result["nodes"] ==  ['foo', 'baz', 'bar', 'baz'])
```

## 5. 中断与恢复如何实现

我们可以节点函数中指定任意值作为参数调用`interrupt`函数实施中断。中断通过`Interrupt`来描述，每个中断具有一个唯一标识（通过id表示），调用`interrupt`方法指定的值对应`Interrupt`的`value`字段。`interrupt`函数本质上是通过抛出`GraphInterrupt`类型的异常实现的。

```python
def interrupt(value: Any) -> Any:
class GraphBubbleUp(Exception):
    pass
class GraphInterrupt(GraphBubbleUp)
    def __init__(self, interrupts: Sequence[Interrupt] = ()) -> None:
        super().__init__(interrupts)

@final
@dataclass(init=False, slots=True)
class Interrupt:
    value: Any
    id: str
    def __init__(
        self,
        value: Any,
        id: str = _DEFAULT_INTERRUPT_ID,
        **deprecated_kwargs: Unpack[DeprecatedKwargs],
    ) -> None
    @classmethod
    def from_ns(cls, value: Any, ns: str) -> Interrupt
```

中断与恢复需要借助LangGraph针对Checkpoint的持久化机制，所以在调用`compile`方法对StateGraph进行编译的时候需要指定一个`BaseCheckpointSaver`对象。由于持久化数据是基于Thread进行存储的，所以在调用Agent的时候需要利用配置指定`Thread ID`。我的专栏文章“[拆解LangChain执行引擎](https://blog.csdn.net/jaydenai/category_13127051.html)”提供了LangGraph持久化的详细介绍。

在如下这个演示程序中，我模拟了一个包含三个步骤的审批流程。三个审批步骤对应`foo`、`bar`和`baz`三个节点函数，第一步`foo`需要人工介入提供审批意见，所以我们调用`interrupt`函数在这里实施中断，该方法返回恢复执行时针对该中断提供的Resume Value。如果提供的“yes”，表示得到许可，此时返回的`Command`将状态字典`is_approved`设置为True，其`goto`字段设置为`bar`，意味着按照正常的流程仅需进行；否则将`is_approved`设置为False，将`goto`字段设置为`__end__`终止整个流程。

```python
from typing import Annotated,Any
from langgraph.graph import StateGraph
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import Command,interrupt,Interrupt
from langchain_core.runnables import RunnableConfig
from pydantic import BaseModel
import operator

class State(BaseModel):
    steps: Annotated[list[str], operator.add] = []
    is_approved: bool|None = None

def foo(state:State):
    approval = interrupt("Need your approval?")
    if approval == "yes":
        return Command(
            update = {
                "steps": ["foo"], 
                "is_approved": True
            },
            goto= "bar"
        )
    return Command(
            update = {
                "steps": ["foo"], 
                "is_approved": False},
            goto= "__end__"
        )       
  

def bar(state:State)->State:
    return State(steps =["bar"])

def baz(state:State)->State:
    return State(steps =["baz"])

agent = (StateGraph(State)
    .add_node(foo) 
    .add_node(bar) 
    .add_node(baz) 
    .set_entry_point("foo")
    .set_finish_point("baz")
    .add_edge("bar", "baz")
    ).compile(checkpointer=InMemorySaver())

def invoke(approval: str, thread_id: str)-> dict[str,Any]:
    config: RunnableConfig = {"configurable":{"thread_id": thread_id}}
    result = agent.invoke(input= State(steps=[]), config=config)
    interrupts: list[Interrupt] = result["__interrupt__"]
    assert interrupts[0].value == "Need your approval?"

    resume = {interrupts[0].id: approval}
    return agent.invoke(input=Command(resume=resume),config=config)

result = invoke("yes", "txt001")
assert result["steps"] ==  ['foo', 'bar', 'baz']
assert result["is_approved"] == True

result = invoke("no", "txt002")
assert result["steps"] ==  ['foo']
assert result["is_approved"] == False
```

我们在编译`StateGraph`时将`checkpointer`参数设置为`InMemorySaver`，意味着我们采用基于内存的持久化方案。我们定义了`invoke`方法对Agent实施中断/恢复调用，两个参数用于指定人工审批意见和Thread ID。我们将Thread ID置于调用Agent提供的`RunnableConfig`配置中，调用Agent的输入是一个`Command`对象，我们将提供的审批意见作为它的`resume`。由于每个节点执行后都会将节点名称添加到状态成员`nodes`中，我们可以看到如果审批意见设置为“yes”，会执行完整的审批流程，并且`is_approved`被设置为True，否则`is_approved`被设置为False,且只有foo节点参与执行。

## 6. 工具在一个怎样的节点中执行？

如果调用`create_agent`工厂函数创建Agent，我们只需要利用其`tools`参数注册所需的工具即可，如果使用采用LangGraph编程模式又该如何使用工具呢？由于LangGraph可以编排具有任意结构的图，所以我们完全可以将工作作为一个节点来定义。

另一个方面，由于`create_agent`工厂函数底层还是使用的LangGraph，它将所有注册的工具封装成一个类型为`ToolNode`。`ToolNode`不仅解决了单纯的工具调用，还在此基础上完成了**流程控制**、**状态注入**、**并发控制**和**异常处理**等工作，它可以直接拿来使用。由于`ToolNode`主要还是为`create_agent`工厂函数创建的Agent设计的，这样的Agent会利用一个`BaseChatModel`以ReAct模式处理请求。`ToolNode`处理的是消息列表，确切来说是消息列表的最后一条携带`ToolCall`的`AIMessage`，所以当我们在LangGraph编程模式种使用它时，必需满足一个基本前提条件：如果输入对象不是消息列表，必需提供一个Key或者字段名输入的字典或者Pydantic模型对象中提取**消息列表**。

```python
class ToolNode(RunnableCallable):
    def __init__(
        self,
        tools: Sequence[BaseTool | Callable],
        *,
        name: str = "tools",
        tags: list[str] | None = None,
        handle_tool_errors: bool
        | str
        | Callable[..., str]
        | type[Exception]
        | tuple[type[Exception], ...] = _default_handle_tool_errors,
        messages_key: str = "messages",
        wrap_tool_call: ToolCallWrapper | None = None,
        awrap_tool_call: AsyncToolCallWrapper | None = None,
    ) -> None:

ToolCallWrapper = Callable[[ToolCallRequest, Callable[[ToolCallRequest], ToolMessage | Command]],ToolMessage | Command]
AsyncToolCallWrapper = Callable[[ToolCallRequest, Callable[[ToolCallRequest], Awaitable[ToolMessage | Command]]],Awaitable[ToolMessage | Command]]
```

上面的代码片段提供了`ToolNode`构造函数的签名，除了表示工具序列的`tools`参数（必需）之外，它还具有如下若干可选参数：

- **name**：节点的名称，默认为`tools`；
- **tags**：为捕捉的跟踪信息提供的标签；
- **handle_tool_errors**：异常处理策略：
  - **bool**: True 表示捕获异常并将错误信息返回给LLM。
  - **str**: 发生错误时统一返回的固定字符串。
  - **Callable**: 一个函数，接收异常并返回自定义的错误描述。
  - **Exception**: 只捕获特定类型的异常。
- **messages_key**：上述用于提取消息列表的Key；
- **wrap_tool_call**：同步工具调用包装器
- **awrap_tool_call**：异步步工具调用包装器。两个包装器提供了类似于AgentMiddleware一样的钩子;

`ToolNode`处理流程很简单：如果输入不是消息列表，而是一个字典或者Pydantic模型对象，它会利用`messages_key`从中提取消息列表，并选择最后一条`AIMessage`。然后进一步从中得到所有的`ToolCall`列表，再利用工具名从自身工具列表中提取匹配的工具，最终以并发的方式执行它们。如果工具返回的不是一个`Command`对象，返回的内容将被封装成一个`ToolMessage`对象，而返回的`Command`将被引擎执行。

`ToolNode`一般作为模型节点的下游，由于模型只有在生成了包含`ToolCall`的`AIMessage`时才会选择执行此节点，所以它们之间是一条**条件边**，我们可以将如下这个`tools_condition`函数作为`add_conditional_edge`的第二个参数。这个函数的返回值为**"tools"**或者**"__end__"**，如果我们的ToolNode具有不同的命名，或者在不需要执行工具时并不需要终止流程，可以利用第三个参数提供一个字典将这两个值映射到具体的目标节点。

```python
def tools_condition(
    state: list[AnyMessage] | dict[str, Any] | BaseModel,
    messages_key: str = "messages",
) -> Literal["tools", "__end__"]:
   
    if isinstance(state, list):
        ai_message = state[-1]
    elif (isinstance(state, dict) and (messages := state.get(messages_key, []))) or (
        messages := getattr(state, messages_key, [])
    ):
        ai_message = messages[-1]
    else:
        msg = f"No messages found in input state to tool_edge: {state}"
        raise ValueError(msg)
    if hasattr(ai_message, "tool_calls") and len(ai_message.tool_calls) > 0:
        return "tools"
    return "__end__"
```

在如下的演示程序中，我们定义了继承自`TypedDict`的状态类型`State`，其中包含唯一字段`messages`维护消息历史。我们创建了三个返回不同时间问候语的工具函数（`get_greeting_for_morning`、`get_greeting_for_afternoon`和`get_greeting_for_evening`），并将其绑定到了`ChatOpenAI`模型对象上。我们定义了模型节点函数`model`，它将状态维护的消息列表作为输入调用`ChatOpenAI`，并将返回的`AIMessage`写入消息列表。

```python
from typing import TypedDict,Annotated
from langchain.messages import AnyMessage, HumanMessage
from langchain_openai import ChatOpenAI
from langgraph.graph import StateGraph
from langgraph.prebuilt import ToolNode, tools_condition
from langchain_core.tools import tool
import operator
from dotenv import load_dotenv

load_dotenv()

@tool
def get_greeting_for_morning() -> str:
    """Returns a greeting message for the morning."""
    return f"Good morning!"
@tool
def get_greeting_for_afternoon() -> str:
    """Returns a greeting message for the afternoon."""
    return f"Good afternoon!"
@tool
def get_greeting_for_evening() -> str:
    """Returns a greeting message for the evening."""
    return f"Good evening!"

tools = [get_greeting_for_morning, get_greeting_for_afternoon, get_greeting_for_evening]
llm = ChatOpenAI(model="gpt-5.2-chat").bind_tools(tools)

class State(TypedDict):
    messages: Annotated[list[AnyMessage], operator.add]

def model(state:State)->dict:
    message = llm.invoke(input= state["messages"]) # type: ignore    
    return {"messages": [message]}

agent = (StateGraph(State)
    .add_node(model)
    .add_node(ToolNode(tools))
    .set_entry_point("model")
    .set_finish_point("model")
    .add_edge("tools","model")
    .add_conditional_edges("model", tools_condition)
    .compile())

message = HumanMessage("What is the greeting for the afternoon?")
result = agent.invoke(input= State(messages=[message]))
for message in result["messages"]:
    message.pretty_print()
```

我们先后将`model`节点和基于三个工具构建的`ToolNode`节点添加到创建的`StateGraph`对象上。`model`节点同时作为入口和完成节点，它与`tools`节点和`__end__`之间具有一条**条件边**，路径选择函数正是上述的`tools_condition`。通过添加`tools`到`model`之间的边使工具执行之后，将结构提交给`model`继续处理。程序执行后，会以如下的形式输出消息列表：

Name: get_greeting_for_afternoon
