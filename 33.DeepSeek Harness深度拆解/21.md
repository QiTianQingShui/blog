# [DeepSeek Harness深度拆解-21]DSH的Session是如何实现的？

DSH和LangGraph的Session的目的相同，都是记录下同一个对话上下文中每一步的状态，并提供**时间旅行**的支持。我们不仅可以从任一时间点重发后续的流程，还能在某个时间点开启一个新的执行流程，相当于开启了**平行世界**。但是两者在实现上不太一样，LangGraph采用Checkpointing的机制，将每个执行步骤（Superstep）的状态以Checkpoint的形式保持下来。而DSH则直接采用Event Source的设计，将构成生命线的每个事件按照发生的顺序记录在一个Apend Only列表中。DSH的Session通过`@deepseek-ai/dsh-session`包提供的同名类型表示，其核心就是通过其`log`字段表示的一个`SessionEvent`列表。DSH基于一段对话的执行流程由一系列通过`SessionEvent`表示的事件组成。在正式介绍`SessionEvent`这个类型之前，我们先来补充介绍几个相关的类型。

## 1. Session完整的执行流程

如下所示的`SessionEventMap`维护了DSH预定义的事件名称和承载对应事件荷载的数据类型之间的映射关系，作为`keyof SessionEventMap`,`SessionEventType`表示这些预定义事件名称字面量的联合。

```typescript
export type SessionEventType = keyof SessionEventMap

export interface SessionEventMap {
  'turn/start': { turn: number }
  'turn/end': { turn: number; reason: TurnEndReason }
  'step/start': { turn: number; step: number }
  'step/end': { turn: number; step: number }
  'user/message': UserMessage
  'system/message': { turn: number; step: number; message: SystemMessage }
  'assistant/message': {
    turn: number
    step: number
    message: AssistantMessage
    stream: AssistantStreamRecord[]
    usage?: TokenUsage
    interrupted?: true
  }
  'assistant/attempt': { turn: number; step: number; stream: AssistantStreamRecord[] }
  'tool/call': { turn: number; step: number; callId: ToolCallId; name: string; arguments: string }
  'tool/result': {
    turn: number
    step: number
    message: ToolResultMessage
    error?: { name: string; code: string }
    meta?: JsonValue
  }
  'request/header': {
    header: EpochHeader
    reason: RequestHeaderReason
    startsSeries?: true
  }
  'request/context': RequestContext
  'session/end-seed': { inherited?: true }
}
```

上面这些预定义的事件类型基本上勾勒出如下所示的一个完整Session内部的执行流程。一个完整的流程由一个或者多个Turn组成，每个Turn对应一次针对Agent的调用。每一轮针对Agent的调用通过ReAct循环形式向前推进，每次循环对应一个Step，并涉及一次针对LLM的调用。每个Turn拥有一个自增的编号作为标识，每个Step在当前的Turn同样具有一个自增的编号，所以Turn和Step的编号的组合唯一标识一个Step。

```mardkwon
Turn：一次Agent调用
└── Step：一次LLM调用
    ├── 输入：user/message
    ├── 系统提示：system/message
    ├── 模型输出：assistant/attempt（未生效） / assistant/message（已生效）
    └── 工具：tool/call → tool/result
```

接下来我们详细介绍定义在`SessionEventMap`中的这些预定义事件和对应的事件荷载类型。

### 1.1 Turn/Step生命周期事件

事件`turn/start`和`turn/end`，以及`step/start`和`step/end`分别作为针对一轮（turn）Agent调用和一次调用LLM步骤（step）的边界。事件`turn/start`和`turn/end`对应的事件荷载内容会携带当前轮次的编号，`step/start`和`step/end`还会携带当前步骤的编号。`turn/end`事件的荷载内容还会提供轮次结束的原因，对应的类型`TurnEndReason`定义如下：

```typescript
export type TurnEndReason = TurnEndReasonMap[keyof TurnEndReasonMap]
export interface TurnEndReasonMap {
  completed: { kind: 'completed' }
  aborted: { kind: 'aborted'; reason: TurnEndCancelCause }
  blocked: { kind: 'blocked' }
  error: { kind: 'error'; error: LlmFailure }
  'max-tokens': { kind: 'max-tokens' }
  interrupted: { kind: 'interrupted' }
}

export type TurnEndCancelCause = AgentCancelCause | { readonly kind: 'legacy' }
export type AgentCancelCause =
  | { readonly kind: 'user' }
  | { readonly kind: 'parent' }
  | { readonly kind: 'hook'; readonly reason: string }
  | { readonly kind: 'disposed' }
export interface LlmFailure {
  readonly message: string
  readonly code: string
  readonly status?: number
  readonly providerRetryAfterMs?: number
  readonly requestId?: ProviderRequestId
}
```

具体的导致轮次结束的原因具有如下这些选项：

- **completed**：正常完成。这一轮正常跑完，模型给出了最终答复、不再需要工具，最常见的收尾方式；
- **aborted**: 实时进行的Agent调用被取消请求中断，`reason`字段会进一步说发起的取消调用当前Agent调用
  - **user**：用户主动发起；
  - **parent**：Parent Agent发起；
  - **hook**：由某个注册的钩子函数发起；
  - **disposed**：Fiber生命周期终结导致；
  - **legacy**：历史遗留记录。
- **blocked**：这一轮被阻断，未能继续推进。无额外载荷，通常表示被策略/前置条件挡住（如输入被拒、被守卫拦截）；
- **error**：出现异常；
- **max-tokens**：达到输出Token上限；
- **interrupted**：程序意外中断。

### 1.2 与消息相关的事件

与消息相关的几个事件最为核心，因为它们最终需要传递给LLM称为其上下文的重要组成部分。可以说Session的一个主要的目的就是为了维护作为对话历史的消息列表，以解决LLM无状态的局限性。基于消息的三种主要角色（`user`、`assistant`和`system`），DSH定义了对应的事件：

- **user/message**：表面看起来就是来源与最终用户的提示词，实际上还包括程序注入的上下文（比如AGENTS.md文件的内容和Skills等），以及 由系统生成的，为了当前任务而推动下一轮对话的消息；
- **system/message**：表示渲染后的系统提示词，对应的事件荷载内容除了携带标识系统消息的`SystemMessage`对象之外，还包含Turn和Step的编号用来标识针对LLM的哪次调用；
- **assistant/message**：LLM返回的响应消息，对应的事件荷载不仅包括Turn和Step的编号、描述完整消息的`AssistantMessage`对象、承载流记录的`AssistantStreamRecord`列表和记录Token消耗的`TokenUsage`。即使在接收过程中被中断，已交付的文本/推理前缀会被定稿成本事件，此时`interrupted`字段会被设置成true；
- **assistant/attempt**：体现一次针对LLM调用的最终并未生效的尝试，比如采用失败重试策略针对LLM的对此调用，最终一次成功的响应会走`assistant/message`事件，前面失败的尝试会走此事件。正因为它表示的始终未生效的尝试，所以事件荷载内容不会包含完整的`AssistantMessage`消息，也不会有承载Token账单的`TokenUsage`。

如果`assistant/message`事件返回的响应涉及到工具调用，每个以分发的工具调用会以`tool/call`事件被记录，事件荷载内容除了包括Turn和Step的编号外、还携带了工具调用ID、工具名称和参数。与`tool/call`事件对应的是`tool/result`，用来表示发送给LLM的工具执行结果，该结构被封装在事件荷载提供的`ToolResultMessage`消息中。

上述相关事件涉及的各种消息类型，`UserMessage`、`AssistantMessage`、`SystemMessage`和`ToolResultMessage`在[DeepSeek Harness深度拆解-06:在自定义插件中体验LLM的动态路由](https://jaydenai.blog.csdn.net/article/details/166201752)中提供了详细介绍。

### 1.3 请求构造

export type SessionEvent<T extends SessionEventType = SessionEventType> = {
  [K in SessionEventType]: {
    type: K
    seq: SessionSeq
    time: number
    data: SessionEventMap[K]
    ignorable?: true
  } & (K extends SurfaceEventType ? SurfaceIntent<K> : {
    surfaceOp?: never
    sourceEventSeqs?: never
  })
}[T]
export type SessionSeq = BrandedNumber<'SessionSeq'>
